UX audit · Mahjong Soul Tournament Tracker

The home page can’t tell you whether it’s working

GET /admin is built as a configuration form, but people open it during a live tournament broadcast. Their question is never “how do I log in” — it’s “is it still tracking?” The page has no answer, and that gap is where the detractors come from.

01The core problem

The page is three stacked cards in a fixed 520px column: Connection (three login tabs plus a tracking-start field), Scoring (uma, starting points, oka), and Overlay (four URLs printed as plain text). On load it calls /api/config and /api/status, then re-polls status every 15 seconds. It never opens a WebSocket and never shows a single piece of live data.

That is a complete answer to the question “how is this configured?” and no answer at all to “is it working right now?” — which is the question an operator has every thirty seconds for the next four hours. Once connected, the page shows a nickname, an account ID, a tracking start time, and an “observer level”. It does not show the contest, the tracked roster, how many games have been picked up, when the last successful poll happened, or a single score. Checking the tool means opening the overlay in another tab and eyeballing it.

Worse, the one status signal it does show cannot fail. connection_status["connected"] is set at login and never invalidated, and every polling exception is swallowed into a log line. The session can expire, the contest can start returning 403s, the network can drop — the dot stays green.

A green light that cannot turn red is worse than no light at all.

02Evidence

Captured from the server running locally on this repo’s config.yaml. The connected state is rendered from the real template against a mocked /api/status, since it is otherwise unreachable without live credentials.

03Where the detractors come from

Three moments produce nearly all of the negative sentiment. Every fix below should be judged against them — anything that doesn’t improve one of these three is polish.

MomentWhat happens todayFixed by
First run A committed .venv that cannot work on Linux, YAML editing, DevTools console instructions, a KeyError crash on an incomplete config, and a green “connected” state that tracks nothing when contest_id is unset. C3, H5, M14
Going live Hand-retyping four localhost URLs into OBS browser sources — URLs that are simply wrong from any second machine, which the default 0.0.0.0 bind invites. H4
Mid-event failure A green dot while polling has been failing for twenty minutes, no way to patch a missed game, and no way to correct the tracking start without a full re-login. C1, C2, H1, H2, H3

04The 25 findings

Every one was reproduced against a running server. Severity is user impact during a live event, not implementation difficulty.

C1

No live tracking state anywhere on the page

Critical

The connected view shows identity, not activity: nickname, account ID, tracking start, observer level. No contest, no roster, no game count, no last-poll time, no scores. The operator cannot verify the tool from the tool.

src/server.py:809–818 — connected view markup; live data already exists at /api/scores and /ws

C2

A green light that cannot turn red

Critical

Every exception in the poll loop is caught and logged, never surfaced. connected is written once at login and never invalidated by downstream failure, so an expired session or a 403ing contest looks identical to a healthy one.

src/tracker.py:692–697 — except Exception: logger.error(...)  ·  src/server.py:276–299 — status never degrades

C3

Silent no-op when contest_id is unset

Critical

Trackers only start if contest_id:. With 0 or a missing key the login succeeds, the page goes green, and nothing is ever tracked — with no warning on any surface.

src/server.py:319–336 — _initialize_connected_trackers

C4

Demo mode is indistinguishable from live

Critical

_initialize_demo_trackers() builds trackers with no client at startup, so the overlay renders the full roster at 0.0 before anyone has logged in. On stream that reads as real data, and the admin page never says otherwise.

src/server.py:302–305, 1378–1382

H1

“Disconnect & Reconfigure” does not disconnect

High

onclick="showSetup()" hides a div. There is no /api/disconnect route — the server stays logged in and polling, and a refresh silently restores the connected view. The label promises something the app cannot do.

src/server.py:817 — button  ·  no disconnect endpoint exists in the route table

H2

Tracking start can’t change without re-authenticating

High

The cutoff is only accepted as a parameter of /api/connect and /api/verify_code, and the field is only reachable through the fake disconnect. Fixing “I started tracking 30 minutes late” — routine on tournament day — means an email round-trip mid-event.

src/server.py:1177, 1220, 1263 — sent only at connect time

H3

Manual result entry is built, tested, and unreachable

High

add_result and reset_player are implemented on the tracker and wired into the /ws command handler. The admin page never opens a WebSocket, so the recovery path for a missed game is invisible to the person who needs it. Best value-per-line fix on the page — the hard part already works.

src/server.py:458–482 — handler  ·  src/tracker.py:712+ — implementation  ·  zero new WebSocket in the template

H4

Overlay URLs are inert, hardcoded text

High

Four http://localhost:8765/... strings printed as <code>: not clickable, not copyable, and wrong whenever the page is opened from another machine or a non-default port. No canvas-size guidance, no transparency note, no preview link. Deriving them from window.location.origin with a copy button is about twenty lines.

src/server.py:934–937

H5

A partial config kills the server with a raw traceback

High

Both the tracker factory and /api/config index config["games_count"] unguarded. Verified: a config missing that key raises KeyError during startup, so the process never boots. A first-run user gets a Python traceback instead of a page telling them which key to add.

src/server.py:171, 530

H6

Everything but scoring needs YAML plus a restart

High

Contest ID, roster, teams, games_count, poll interval and server region are file-only. The page that is meant to run the tournament can change six numbers and nothing else.

config.yaml, config.semifinals.yaml — read once at import

H7

Observer status is internal vocabulary

High

observerSummary() renders reported level 2. Nothing says what level this contest requires, whether the account qualifies, or what to do if it doesn’t — and when observer_error is set, the amber failure text sits under a green dot.

src/server.py:1057–1061, 1070–1079

M1

No <form> element — Enter never submits

Medium

Zero <form> tags in the template. A user types a six-digit code, presses Enter, and nothing happens — inside a timed verification window.

src/server.py:836–891 — bare inputs plus onclick

M2

Code field fights the user’s keyboard

Medium

type="text" maxlength="10" for a six-digit numeric code, with no inputmode, no autocomplete="one-time-code", and no autofocus on the field the user just navigated to.

src/server.py:852

M3

No resend or countdown on the verification code

Medium

If the mail is slow the only route is “Back”, which resets the whole step. Nothing indicates how long to wait.

src/server.py:847–855

M4

Login tab isn’t remembered; saved UID never prefills

Medium

Token users re-click the same tab every session. And admin_page() does ADMIN_HTML.replace("__DEFAULT_UID__", uid) against a template that contains no such placeholder — dead code, while config.yaml already stores the UID.

src/server.py:736

M5

Raw Python exceptions shown as user-facing errors

Medium

Users see 403, message='Attempt to decode JSON with unexpected mimetype: text/plain', url=... — and it is injected via innerHTML. Map the handful of common failures to plain language; keep the raw text behind a details toggle.

src/server.py:1162, 1206, 1250 — str(e) straight to the DOM

M6

Status condition is unreadable and probably wrong

Medium

if (s.error && !el.classList.contains('hidden') === false). Since !x === false reduces to x, this only surfaces errors while step 2 is hidden — almost certainly not the intent, and unreadable either way.

src/server.py:1123

M7

Scoring saves silently and widely

Medium

No presets for common rulesets, no unsaved-changes indicator, no confirmation before a save that recalculates every finished game, and no mention that it writes both config files.

src/server.py:609–623 — writes player and team configs

M8

Mobile overflows horizontally

Medium

At 390px the three-tab flex row will not shrink below its content width, so the page scrolls sideways and inputs run off screen. The only media query addresses the scoring grid. Fix: flex-wrap: wrap plus min-width: 0.

src/server.py:773–777, 795–797

M9

Desktop wastes most of the viewport

Medium

A single 520px column pinned left on a 1280px screen. Two columns above ~900px would let a live status panel sit beside the forms with no scrolling — which is exactly what C1 needs room for.

src/server.py:749–750 — .card { max-width: 520px }

M10

Tabs are <div onclick>

Medium

Not focusable, no role="tab", no keyboard support, and there is no :focus-visible styling anywhere on the page.

src/server.py:822–826

M11

Help text falls below AA contrast

Medium

.help { color: #555 } on #0e0e14 is roughly 3:1. Several help strings are patched inline to #bbb, which suggests the base value was already known to be too dim.

src/server.py:792

M12

Login form flashes on every load

Medium

The setup form renders visible, then hides once /api/status resolves, so connected users see a login screen flicker on every refresh. A neutral loading state removes it.

src/server.py:821, 1366–1368

M13

No favicon; the title carries no state

Medium

/favicon.ico 404s and the tab reads a static Tracker Admin while the heading says Mahjong Soul Tracker. For a page that lives in a pinned tab all day, a status-bearing title (● Tracking · 12 games) is free reassurance.

src/server.py:744 — <title> vs 801 — <h1>

M14

The literal home page is a JSON 404

Medium

There is no root route. GET / returns {"detail":"Not Found"} — verified. One RedirectResponse to /admin fixes it.

src/server.py:486–736 — route table has no /

05What “working” should look like

The fix for C1 and C2 is one idea: the status light must be able to fail, and it must say what it knows. Track the outcome of each poll in GameTracker, expose it on /api/status, and render three honest states instead of one permanent green.

Today

Connected as BroadcastBot

Account ID 123885514 · Contest observer info: reported level 2

Proposed

Tracking · contest 970393

4 players · 6 of 16 games in · last update 4s ago

Both panels are showing a healthy tracker.

Beyond the light, the connected view has room for the things an operator actually checks: contest ID and name, the tracked roster or teams, games completed against games_count, the tracking cutoff as both a timestamp and a relative age, and a compact score table straight from /api/scores. All of that data already exists on the server — none of it reaches this page.

06Roadmap

Ordered by NPS movement per day of work, not by severity. Phase 1 is where the trust deficit lives; phase 2 is mostly wiring up capability the backend already has.

Phase 1 · Make it trustworthy

1–2 days · fixes C1–C4, H7
  1. Turn the page into a dashboard. Live status card: contest, roster or teams, games detected, last successful poll (“updated 4s ago”), compact score table. Reuse /api/scores and /api/scores/team, or subscribe to /ws for push.
  2. Let failure show. Record last-poll outcome in GameTracker, expose it on /api/status, render Tracking / Degraded / Not connected with the reason.
  3. Warn loudly when contest_id is unset or the observer level is insufficient — in plain language, with the fix.
  4. Label demo mode explicitly, on the admin page and the overlay alike.

Phase 2 · Remove the dead ends

1–2 days · fixes H1–H5
  1. Expose manual result entry (add_result / reset_player) — the backend is done and tested.
  2. Add POST /api/tracking_start to move the cutoff without a re-login, and surface the field in the connected view.
  3. Add a real POST /api/disconnect, or rename the button to what it does.
  4. Derive overlay URLs from window.location.origin, with copy buttons, preview links and OBS notes.
  5. Guard required config keys and fail with an actionable message plus a config-health line on the page.

Phase 3 · Polish

~1 day · fixes M1–M14
  1. Wrap inputs in a <form>, add autofocus, inputmode="numeric", maxlength="6", code resend, remembered login tab, prefilled UID.
  2. Keyboard-accessible tabs, visible focus rings, higher help-text contrast.
  3. Fix the mobile overflow; add the two-column desktop layout that phase 1 needs.
  4. Loading state instead of the login flash; favicon; status-bearing <title>; friendly error mapping; scoring presets and unsaved-changes indicator; / redirects to /admin.

Phase 4 · Bigger bets

multi-day · fixes H6
  1. Edit contest ID, roster, teams and games_count from the UI, hot-reloaded without a process restart. This is what finally makes the tool self-service.
  2. Extract ADMIN_HTML into overlay/admin.html — 630 lines of HTML and JS inside a Python string get no highlighting, no linting and no tests — then cover the admin API surface with tests.

07How to tell if it worked

The three detractor moments map onto observable events. Instrumenting them locally is enough to see whether a score movement is real rather than seasonal:

  • Time from server start to first successful poll — first-run friction.
  • Share of sessions that ever enter Degraded, and how long they stay there.
  • Whether manual result entry gets used at all — a proxy for tracking accuracy gaps.
  • Overlay-URL copies per session — a proxy for OBS setup friction.

If a survey is added, fire it when a tournament session ends, not on the config page. Asking for a score in the middle of setup measures the survey, not the product.

08Method & other notes

Findings were produced by running python -m src.server against this repo’s committed configs, probing every route with curl, exercising failure paths directly against the app callables, and screenshotting the page in Chromium at 1280px and 390px. Line references are to main at commit c06953d.

Outside the page, worth acting on anyway.

config.yaml is committed with what appears to be a live yostar_token and yostar_uid. If those are real, rotate them and ship an example file instead.

.venv/ is committed — 1,467 files — and it is a macOS virtualenv whose python3 symlinks into Xcode, so it cannot work on Linux and breaks the documented setup for anyone who trusts it. Add .venv/ and __pycache__/ to .gitignore and drop them from the index.

Startup blocks on a Majsoul pre-connect inside the startup event. It fails fast when the host is unreachable, but a slow connect delays application startup — and the admin page with it.
